# Drift-Aware Adaptive Edge–Cloud–Hybrid Orchestration for Non-Stationary IoT Systems

A reproducible, research-grade simulation of an industrial IoT system that operates under
non-stationary data, limited Edge resources, and variable network conditions.

**Status: Phase 1 complete** — configuration, utilities, data loading, drift injection, streaming,
causal preprocessing, feature extraction, a 230-test suite, and a reproducible end-to-end
demonstration.
No Phase 2+ functionality is implemented. See [Implementation status](#implementation-status).

## 1. Research question

> Does incorporating online prediction drift and reliability into Edge–Cloud orchestration
> improve post-drift prediction performance while maintaining acceptable latency and resource
> consumption compared with existing approaches?

### Hypothesis under test

> If we apply drift-aware reliability-based adaptive Edge–Cloud–Hybrid orchestration to
> non-stationary heterogeneous IoT data streams, then post-drift Macro-F1 will improve relative
> to the HECIF-style adaptive Edge–Cloud baseline without drift-aware orchestration, while
> satisfying latency and Edge resource constraints under controlled data and network shifts.

This is a hypothesis to be **tested, not assumed**. An exploratory target of ≥10 % relative
improvement may be used for pilot sizing, but it is **not** a guaranteed or hard-coded outcome.
If the proposed method performs worse in a scenario, that result will be reported.

## 2. Causal chain

The simulation must demonstrate this loop end-to-end:

```
IoT Data → Streaming → Data Processing → Edge ML Prediction → Prediction Error
    → ADWIN → Drift Detection → Reliability Assessment
    → Network + Edge Resource Monitoring → LRI → Weighted Decision Score
    → Edge / Cloud / Hybrid → Final Prediction → Performance Feedback
    → Persistent Drift Check → Model Adaptation → Updated Model → Continue Streaming
```

The decision is **calculated**, never asserted:

```
WDS(a) = w1·LRI_a + w2·E_a + w3·B_a + w4·(1 − R_a) + w5·C_a      for a ∈ {Edge, Cloud, Hybrid}
a*     = argmin_a WDS(a)
```

There is deliberately **no** `if drift then Cloud` rule anywhere in the controller.

## 3. Central data principle — does not change

> **Real HAI is the foundation. Controlled synthetic drift is applied *to* HAI.**

```
Real HAI → Controlled synthetic drift injection → Drifted HAI → Inference stream
```

`src/data/generator.py` therefore injects controlled drift into real HAI observations.
It is **not** an independent IoT sensor-data generator and must never fabricate a
replacement for HAI.

| Directory | Contents |
|---|---|
| `data/raw/` | The actual HAI files, unmodified |
| `data/processed/` | Preprocessing outputs where appropriate |
| `data/synthetic/` | Streams **derived from HAI** by controlled drift injection |

### Dataset currently supplied

**HAI 23.05** (HIL-based Augmented ICS Security Dataset), six files copied verbatim into
`data/raw/`, SHA-256 verified byte-identical to the user's originals. Provenance, checksums,
and every measured diagnostic: `data/raw/PROVENANCE.json`.

The release is identified **from file contents, never from names or sizes**: one byte-identical
87-column set across all four process-value streams, the `x100*` setpoint/assign/sum channels
absent from earlier releases, attack labels shipped in **separate sidecar files** rather than as
a column, and exactly train1/train2/test1/test2 as the released split. Revisions 1–4 of
`PROVENANCE.json` called this "22.04"; that attribution had never been measured and is corrected
there rather than quietly replaced. `train3`/`train4` are excluded from the first experiment and
are declared in no configuration, so no code path can reach them.

Despite the `.txt` extension the files are **comma-separated with a header row**.

Three sections with three meanings, and the separation is enforced rather than documented:
`dataset.files` holds **process-value streams only**, because `loader.file_specs()` treats every
entry in it as either the one inference stream or a baseline candidate — a label sidecar listed
there could be selected as training data and normalised as if it were plant data.
`verify_step2.py` check 4 fails if any entry of `dataset.files` so much as looks like a label
file, and requires every active sidecar to name a declared stream and carry
`alignment: elementwise_verified`.

| Property | Value (measured across the four process-value files) |
|---|---|
| Columns | 87, byte-identical column set in all four files |
| Timestamp column / format | `timestamp`, `%Y-%m-%d %H:%M:%S` |
| Sampling | Exactly 1 Hz — **0 gaps**, max step 1.0 s |
| Chronological | Monotonic, **0 duplicate timestamps** |
| Missing cells | **0** |
| Non-numeric columns besides timestamp | none |
| Label column | **none — the labels ship as separate sidecar files; see below** |

| Cardinality profile (train1, threshold 10) | 58 continuous / 28 discrete (6 binary) |

The files are **kept separate** and never concatenated (`dataset.concatenate_files: false`).

> #### Resolved — the target, from the official HAI label sidecars
> **This was the user's decision, not a model's.** The process-value files contain no
> attack/anomaly column, and the original Step 2 finding stands on the record: all 87 column names
> are identical across train1/train2/test1 (so test1 has no extra column); a name scan for
> label-like identifiers matched nothing; and a structural probe for *"constant in both training
> files but varying in test1"* — the signature an appended label would have — returned nothing.
> Per the standing rule *"if labels are absent, do not fabricate them"*, no label was invented and
> `dataset.task` stayed `unresolved` for as long as that was the honest state.
>
> HAI 23.05 ships the labels **in a separate file per test stream**. `dataset.task` is now
> `labels_from_hai_labels`, `label_column: label`, `positive_class: 1`, `target_column: null` —
> no process channel is the target. **Post-drift Macro-F1 is preserved as the primary metric.**
>
> **Adopted only after alignment was proven, not assumed.** Matching row counts and matching
> first/last timestamps do not establish alignment: a dropped second in one file and a duplicated
> second in the other cancel out in both summaries while shifting every label by one row.
> `audit_alignment.py` compares the full timestamp vectors position by position, and passes 6/6 on
> `hai-test1` ↔ `label-test1`: 54,000 labels for 54,000 rows, timestamps equal **elementwise** on
> all 54,000, identical timestamp sets, unique label stamps, 0 missing, 2 classes. Class
> distribution **0: 51,019 (94.4796 %) / 1: 2,981 (5.5204 %)** in **14 contiguous attack
> episodes**. That 5.52 % positive rate is also why the metric is Macro-F1 and not accuracy — a
> majority-class predictor already scores 94.48 %.
>
> **Quarantined.** `dataset.label_usage: evaluation_only`, with 13 forbidden consumers (models,
> drift detectors, severity, persistence, reliability, controller, WDS, LRI, Edge, Cloud, Hybrid,
> adaptation, preprocessing) and `label_allowed_consumers: [metrics, plots,
> statistical_evaluation]`. Official HAI labels and controlled synthetic-drift ground truth are
> **two different objects and are never merged**: one is what the plant did, the other is what we
> injected.
>
> `resolve_target()` has not become lenient — it still raises for any config that names no label
> source, and `verify_step3.py` check 4 now pins four statements where it previously pinned one.

> #### Open finding — the causal baseline is unlabelled (`finding_training_labels_absent`)
> HAI 23.05 ships label files for the **test** streams only. There is none for train1 or train2,
> so the one causally valid baseline carries no labels. Assigning `label = 0` to every training
> row would be fabricating labels; HAI's documented intent is that the training files are
> attack-free normal operation, but that is the distribution's claim about its own data, not
> something measurable from files that ship no labels.
>
> Recorded, not resolved: `dataset.training_labels_available: false`, ASSUMPTION [A18] —
> *train1 is treated as unlabelled, NOT as all-normal.* Whether the Edge/Cloud models are
> therefore one-class/reconstruction detectors or supervised under an explicit attack-free
> assumption is a **Phase 2 model-design** decision and is left to the user. The third option —
> carving a labelled development split out of test1 — is rejected in advance as leakage, and is
> already refused by `allow_acausal_baseline: false` and `loader.profile_baseline`.

> #### Open finding — `label-test2` is minute-resolution (`finding_label_test2_minute_resolution`)
> `audit_alignment.py` passes only **3/6** on `hai-test2` ↔ `label-test2`. The row count matches
> exactly (230,400) with 0 missing labels and 2 classes, but the label timestamps are
> minute-resolution — textually `2022-08-17 0:00` — giving **3,841 distinct stamps for 230,400
> rows** (226,559 duplicates) and **226,560 rows disagreeing elementwise**; the label file also
> starts at `00:00:00` against the stream's `00:00:01`.
>
> Positional alignment is *plausible* — a row count matching to the row would be a striking
> coincidence otherwise — but **unverifiable from the timestamps**. Assuming it would silently
> offset every label by up to 60 s, and a 60 s offset against 38 attack episodes in a 1 Hz stream
> would corrupt exactly the boundaries detection latency is measured at. So `hai-test2.txt` and
> `label-test2.txt` are declared under `dataset.reserved_files`, a section **no loader code path
> reads** — structurally unreachable rather than switched off by a flag someone could flip. The
> stream file itself is sound (exact 1 Hz, 0 gaps, 0 duplicates, 0 missing); only its labels block
> it. The honest cheap fix — verifying that each minute-stamped block covers exactly 60
> consecutive stream rows — is named and deliberately **not** taken here: test2 is not the first
> experiment.

> #### Blocker 2 — train2 lies in test1's future
> Measured chronological order is **train1 < test1 < train2 < test2** — not the order the
> filenames imply. test1 ends `2022-08-13 07:00:00` and train2
> begins `2022-08-13 07:00:01`, one second later. Training a baseline on train1 + train2 would fit
> on data recorded *after* the inference stream — temporal leakage regardless of labels.
>
> Resolved in configuration, not in code: `dataset.baseline_source: train1_only`
> (ASSUMPTION [A17]), `dataset.allow_acausal_baseline: false`, `split.mode: separate_file`.
> Cost: the baseline is 280,800 rows (78 h) instead of 572,400 (159 h). A smaller causal baseline
> is scientifically valid; a larger acausal one is not.
>
> **Re-measured on 2026-08-27 with test2 present, and confirmed rather than assumed to still
> hold.** train1 remains the only file recorded entirely before test1. test2 being the latest
> stream would have admitted a *larger* legitimate baseline, which is precisely the temptation the
> re-measurement was run against.

> #### Leakage trap — command/feedback sibling pairs
> HAI encodes six actuators as `D`/`Z` sibling pairs — `D` = command sent, `Z` = position fed
> back: `P1_FCV01`, `P1_FCV02`, `P1_FCV03`, `P1_LCV01`, `P1_PCV01`, `P1_PCV02`. If one member
> were ever the prediction target while its sibling stayed a feature, the task would collapse to
> near-triviality. Recorded as `dataset.features.command_feedback_pairs` with
> `exclude_target_sibling: true`.

> #### Open finding 1 — near-collinear channel pairs beyond the `D`/`Z` list
> Measured on the train1 baseline (Step 3): **four** continuous pairs exceed |Pearson r| > 0.999,
> and none of them are in `command_feedback_pairs`, which covers only the six `P1_` actuators.
>
> | Pair | r |
> |---|---|
> | `P1_FT02Z` ↔ `x1003_10_SETPOINT_OUT` | +0.99969632 |
> | `P1_TIT01` ↔ `P4_ST_TT01` | +0.99967895 |
> | `P4_ST_GOV` ↔ `P4_ST_PO` | +0.99932143 |
> | `P3_LCV01D` ↔ `P4_HT_PO` | +0.99904248 |
>
> Three of these involve channels that `drift.affected_features.selection: top_variance` picks.
> Injecting drift into one member while its twin stays as recorded produces a physically
> inconsistent state, and gives any model an untouched proxy from which to compensate — the same
> hazard class as the `D`/`Z` trap. **Not silently changed:** selection behaviour is unaltered.
> Two configuration routes exist (`drift.affected_features.explicit`, or extending
> `command_feedback_pairs`); choosing one is a scientific decision, recorded in `PROVENANCE.json`.

> #### Open finding 2 — `top_variance` selects continuous control commands, not only sensors
> `drift.affected_features.actuator_policy: exclude` filters **discrete** channels. Two of the
> five channels it selects for the single-drift scenarios are continuous *command/demand*
> channels: `P3_LCV01D` (1,135 distinct values, −176 … 19,408) and `P3_LCP01D` (1,731 distinct,
> −16 … 13,824). Offsetting a setpoint means "the controller is told the wrong thing", which is a
> different physical story from sensor measurement bias — arguably a legitimate control-loop
> miscalibration drift, but a different one. **Not silently resolved**; recorded for decision.

> #### Open finding 3 — the 3×IQR outlier rule degenerates on constant setpoints
> `preprocessing.outliers.method: iqr` with `iqr_multiplier: 3.0` collapses to a **zero-width
> band** whenever `q1 == q3`, which happens for piecewise-constant ICS channels. Measured on
> train1 → test1: **2 of 58** continuous channels are degenerate — `P1_PP04SP` (q1 = q3 =
> 27.98469; constant at 27.48882 throughout test1, so **100 % of rows flagged**) and `P1_PCV02D`
> (q1 = q3 = 12.0; 0.32 %). `P4_HT_FD` is near-degenerate (IQR = 3.6 × 10⁻⁴, 13.57 %). The
> row-level flag therefore **saturates at 100 % and carries no information**; excluding the two
> degenerate channels gives **22.98 %**, with a worst per-channel rate of 8.33 % (`P2_SCST`).
>
> Scope of the damage is bounded and measured: `action: flag` alters no value and drops no row
> (checks 5–7), and flags are metadata — never columns of the feature matrix — so nothing can leak
> into a model. Only the diagnostic is degraded. **Behaviour unchanged**; the degeneracy is now
> self-reporting (`QualityReport.degenerate_bound_columns`, plus both flag rates in every run).
> Four resolution options in `PROVENANCE.json` → `finding_degenerate_outlier_bounds`.

> #### Finding 4 — test1 is already shifted from train1 before any drift is injected
> Measured on the **clean** stream, in frozen baseline σ: **8 of 66** features sit more than 1 σ
> from their baseline mean, **1** exceeds 3 σ (`P1_PP04SP` at **−3.96 σ**, and constant within
> test1 — zero-variance in the inference stream although not in the baseline, so the loader did
> not drop it). Mean |z| = 0.4546, median 0.3064.
>
> This is a property of the real recordings, not a defect, and it must stay uncorrected —
> re-centering test1 on its own statistics would be leakage *and* would cancel the injected drift.
> It does **not** confound the primary measurement: the offset is flat across the stream, so the
> clean-stream post-minus-pre shift is only **−0.0365 σ** against **+1.7586 σ** on the drifted
> stream, and `verify_step4.py` subtracts the clean figure explicitly. What it *does* mean is that
> a drift detector will see genuine shift from row 0, so **Phase 3 detection latency must be
> measured relative to the injected onset with the detector allowed to settle on the pre-drift
> segment** — not from stream start.

> #### Superseded: SWaT
> SWaT was the previous primary dataset. The supplied `attack.csv` contained **54,621 `Attack`
> rows and 0 `Normal` rows** — a single-class target, and Macro-F1 is degenerate with one class.
> Two rescues were investigated and rejected on measured evidence, retained in
> `PROVENANCE.json` under `superseded_swat_record`:
>
> - *Predict an actuator state instead of the attack label* — **rejected.** SWaT actuators are
>   PLC-controlled by deterministic sensor thresholds, so the target is trivially recoverable
>   (chronological-split test Macro-F1 up to **1.0000**). That leaves no accuracy headroom, forces
>   `R_edge ≈ R_cloud`, and prevents post-drift Macro-F1 from showing degradation or recovery.
>   **This probe is the precedent any HAI `state_classification` target must survive.**
> - *Concatenate the SWaT Normal file onto this subset* — **rejected.** The join would introduce one
>   large artificial regime change, making ADWIN detections unattributable to the injected drift.
>   This is also why `dataset.concatenate_files` is false for HAI.
>
> `attack.csv` is still present in `data/raw/` and is referenced by no configuration.
> **No substitute or fabricated data has been created at any point.**

## 4. Scientific constraints — project-wide

These apply to every phase and are treated as correctness requirements, not guidelines.

1. **No data leakage.** Future information must never influence past preprocessing, inference,
   or decisions. This includes *file-level* leakage: no baseline statistic may be fitted on a
   file recorded after the inference stream.
2. **Online / causal normalization.** Normalization statistics update causally from observed
   samples only. `scaler.fit(all_data)` is prohibited — it would leak post-drift information.
3. **Ground-truth isolation.** Synthetic drift timestamps and parameters are **evaluation-only**.
   They are never exposed to models, drift detectors, reliability estimators, controllers, or
   Edge/Cloud components.
4. **Learnable-then-changed behaviour.** The pre-drift baseline must contain genuinely learnable
   industrial behaviour before the drift event.
5. **Preserve genuine drift.** Preprocessing must not delete the post-drift observations the
   experiment exists to detect. Outlier handling is therefore conservative by design.
6. **Reproducibility.** Every experiment is reproducible from configuration + random seed.
7. **Real industrial foundation.** HAI remains the real source dataset; "synthetic" means
   controlled transformation *of* HAI.
8. **No fabricated results.** Metrics are reported only after experiments actually run.
9. **No fabricated labels.** The label is **read from the distribution**, never manufactured or
   derived from process values, and only after its alignment to the stream was proven
   elementwise. Where labels are absent — as they are for the causal training baseline — they
   stay absent (ASSUMPTION [A18]) rather than being assumed to be all-normal.

### Information available to the controller at time *t*

| May use | Must **not** use |
|---|---|
| Current network conditions | Future labels |
| Current Edge resources | Future errors |
| Recent prediction errors | Future drift / true drift timing |
| Current prediction confidence | Future network conditions |
| Current ADWIN state, reliability | Future model performance |
| Current model metadata | Post-drift data before it arrives |

The suite is deliberately adversarial about the things that would invalidate results rather than
merely break the code: `tests/test_integrity.py` tokenizes every `src/` module and fails on a
`.fit(all_data)`, a `shuffle=True`, a `.shift(-1)`, a hard-coded metric value, or a literal
`return "cloud"`. It distinguishes prose from code — a docstring naming a forbidden construct in
order to explain it is not an offence — and `test_the_source_scanner_itself_can_still_see_an_offence`
plants a real violation beside prose mentions of the same constructs, so the scanner cannot
silently become vacuous.

#### Three defects the suite found that the four verify harnesses had missed

Reported because they were real, and because a suite that finds nothing has not been tested:

1. **`src/utils/config.py` — `require()` could never report more than one missing key.** It passed
   the module's own "no default supplied" sentinel into `get()`, so `get()` raised on the first
   absent path and the aggregation branch was unreachable dead code. Fixed with a local sentinel;
   it now lists every missing key at once, which is the point of a start-of-run assertion.
2. **`src/data/loader.py` — `BaselineProfile.sigma()` handed back an unusable scale.** For a channel
   dropped as zero-variance it returned `0.0`, contradicting its own docstring; any caller dividing
   by it would silently produce `inf`/`nan` inside a drift-magnitude calculation. It now raises.
   (Audited: only members of `profile.continuous` are ever passed to it, so no live call site
   changed behaviour.)
3. **`src/data/preprocessing.py` — a leakage guard that fired only on data that happened to have
   holes.** `_impute()` validated `interpolate_direction` *after* short-circuiting on "no missing
   cells". test1 contains zero missing cells, so an acausal `interpolate_direction: both` passed
   silently there and would have failed only on a stream with gaps — the same configuration
   accepted or rejected depending on the input. The validation is now hoisted above the
   short-circuit, with `test_the_imputation_guard_does_not_depend_on_the_data_having_holes`
   pinning it.

### Continuity across sessions and models

Development spans sessions and, deliberately, different models and APIs. Assistant-local
memory does not cross that boundary, so the context that has to survive lives in the
repository as three artifacts with different decay properties:

| Artifact | Nature | Rule |
|---|---|---|
| `AGENT_CONTEXT.md` | the contract — prohibitions, protocol, bootstrap, gotchas | read first; hand-maintained |
| `DECISIONS.md` | reasoning behind every decision, error and fix | **append-only**; never rewritten |
| `PROJECT_STATE.md` | implementation status, blockers, guards, inventories | **generated** by `state_report.py`; never hand-edited |

The split is the whole design. Status decays and must therefore be measured off the tree on
demand; reasoning does not decay and must therefore be permanent. A hand-written status
document is correct on the day it is written and silently wrong afterwards — and a
confidently stale handover is worse than none, which is the failure mode the rest of this
project spends 230 tests preventing elsewhere.

`PROJECT_STATE.md` embeds a fingerprint over the code, config and provenance surface it read.
`state_report.py --check` recomputes it and exits non-zero when the tree has moved, so
staleness is detectable rather than merely regrettable. `verify_handover.py` runs that check
and eleven others — including that `AGENT_CONTEXT.md` and this README quote **identical**
verification counts, and that no finding recorded as awaiting a user decision is missing from
the log. It is deliberately **not** part of `pytest`: regenerating state is a session-end
ritual, and wiring staleness into the suite would leave it red during ordinary development,
destroying the signal that a green suite currently carries.

At the end of a working session:

```bash
cd drift_aware_edge_cloud && ../.venv/Scripts/python.exe state_report.py --write && ../.venv/Scripts/python.exe verify_handover.py
```

Macro-F1 preserved. The two options not taken keep their measured consequences in `PROVENANCE.json`. |
| **Labels for the causal baseline** | **Open, Phase 2 model-design.** HAI labels the test streams only, so train1 is unlabelled (ASSUMPTION [A18]). One-class/reconstruction versus supervised-under-an-attack-free-assumption is left to the user; a labelled split carved out of test1 is rejected as leakage. |

## 10. Research integrity

- Baselines, ablations, and the proposed method use one identical evaluation protocol.
- The proposed method is not tuned on test results, and weights are not selected after
  inspecting only its own outcome.
- ≥10 random seeds per experiment; mean, standard deviation, and confidence intervals reported,
  with significance testing where appropriate. No seed cherry-picking.
- Negative and unfavourable results are reported.
